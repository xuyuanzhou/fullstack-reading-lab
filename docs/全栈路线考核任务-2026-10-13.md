## 1. 通用考核规则

每关题号稳定为 `Gx-W1/W2/W3`（笔试）、`Gx-P1`（实操）、`Gx-I1`（模拟面试）。预备用 G0，任务名不改变现有站内 gate id。框架专项增加 R/V 后缀；一个框架通过不能自动替代另一个。

笔试每题 10 分：结论 3、机制 4、边界或反例 3，三题至少 21 分。不是逐字匹配参考要点；有条件的不同方案，只要论证成立可以得分。

实操逐项检查，不用平均分抵消核心错误。口述按需求澄清、机制、证据、取舍四项各 0～4 分，全部至少 3 分通过；得分定义沿用总方案能力尺度。新手诊断不设置淘汰线，只标出先修缺口。

每项任务记录：能力编号、题版本、输入/约束、允许工具、证据文件、原始执行结果、评审方式（自评/同伴/自动检查）、下一步。自动测试证明行为，不自动证明理解；AI 给出的判分只能标“建议”，不能冒充人工面试结论。

参考要点默认在提交尝试或主动请求后展开。失败反馈须指出“哪个行为不符、已有证据、下一步检查”，不得只给“错误”。允许提示、重试、暂停；不扣经验、不倒退关卡。

## 3. G1：走通双端业务

能力：J01/J04、R01/V01、F01、W01。依赖：G0 的编程、Web、SQL 基础。

| 题号 | 笔试题 | 判分要点 |
| --- | --- | --- |
| G1-W1 | 禁用提交按钮能否保证库存不超卖？ | 不能；UI 改善体验，后端约束与事务保证持久化；脚本和多客户端可绕过 |
| G1-W2 | React 的 state 更新后当前事件里读到什么？Vue `ref` 更新后何时能读到新 DOM？ | React 当前闭包通常仍为该次渲染快照；Vue 值改变与 DOM 批量更新分开，必要时 nextTick；两边都不把调度当同步 DOM 保证 |
| G1-W3 | Spring 控制器单例中保存“当前用户”字段会怎样？ | 请求间共享可变状态；身份从请求上下文显式传入用例；不通过把所有组件改多例掩盖模型错误 |

G1-P1：React 用户端提交订单，Vue 管理端展示订单，Java 服务保存到真实数据库；先做模块化单体。

- 两框架均展示加载、空数据、成功和失败；一个请求失败后输入保留，可重试。
- 五类失败分别标出页面/接口/用例/持久化落点：非法字段、业务拒绝、唯一冲突、事务回滚、网络未达。
- 带最小身份检查、结构化日志和请求相关 ID；该身份实现限测试环境，G4 再深化。
- CI 至少运行 Java 测试、前端类型检查及一个组件测试；不得以“G5 才学测试”为由跳过。
- 提交契约、启动说明、真实 React/Vue/Spring 源码和一份 PR 评审；禁止只有截图或注释桩。

G1-I1，15 分钟：“用户说按钮转了一圈但不知道成功没有，你分别在哪四处查？”追问断网发生在服务提交前后是否相同。

## 4. G2：事务、并发与幂等

能力：J02/J04/J05、D01。依赖：G1，SQL 约束、基本测试。

| 题号 | 笔试题 | 判分要点 |
| --- | --- | --- |
| G2-W1 | 为什么两个事务都查到库存 1 仍可能超卖？MVCC 能否替代条件更新？ | 快照读取不等于独占写入；条件更新/锁/版本检查要在正确事务边界；检查受影响行数 |
| G2-W2 | `this` 调用、捕获异常、`REQUIRES_NEW` 各如何影响 Spring 事务？ | 代理边界；是否设置 rollback-only/异常规则；独立事务可单独提交并增加连接需求，不等于嵌套保存点 |
| G2-W3 | 同幂等键但不同请求体应该返回什么？响应丢失后怎样重试？ | 检查请求语义/摘要并拒绝冲突；并发唯一约束与业务效果原子性；原键重试查询结果，不生成新键 |

G2-P1：库存初始为 1，使用同步起跑点启动至少 20 个竞争请求；另用同业务键并发重复请求。

- 不同业务请求仅一笔成功、最终库存 0；同业务键只有一次业务效果。返回结果以契约为准，不能只数 HTTP 200。
- 无任意 sleep 作为正确性前提；提交后使用独立数据库连接校验，避免测试事务遮蔽行为。
- 模拟提交前异常、提交后响应丢失、同键异参、唯一冲突；每个有测试名。
- 持久化选 JPA 或 MyBatis 为主；另一种在最小实验中实现同一版本条件并测试。
- 结构来自迁移脚本，重新建库可重放；保留执行命令、原始测试结果和失败时序。

G2-I1，20 分钟：“如何保证不会重复扣减？服务器在任意两步间崩溃时分别怎样恢复？”追问不变量、幂等结果保留期和事务外部副作用。

## 5. G3：读取与双框架机制

能力：D01～D03、R02/V02。依赖：G2，闭包/Promise/对象身份。

| 题号 | 笔试题 | 判分要点 |
| --- | --- | --- |
| G3-W1 | 排序字段不唯一时，keyset 分页为何仍会重复或漏项？ | 需要唯一排序组合与相应游标；过滤条件和排序一致；并发修改语义另约定 |
| G3-W2 | 写库后删缓存为何仍可能读旧值？ | 读未命中读取旧库值，写提交删缓存后读再回填；展示时序和可接受一致性边界，不宣称一招强一致 |
| G3-W3 | React 请求闭包与 Vue 解构响应式对象分别会出现什么错误？ | React 依赖/清理/请求竞态；Vue 基本值脱离代理追踪；分别修复，不把两者解释为同一种响应式 |

G3-P1：加入分页、缓存，并在 React/Vue 中快速切换筛选，控制后发请求先返回。

- 固定合成数据集，记录 N+1 优化前后的 SQL 次数与查询计划；包含空页和重复排序值。
- 可重复演示缓存竞态，写明一致性选择；不能通过删除失败测试掩盖窗口。
- React 用请求标识、取消或数据层等合理方案避免旧结果覆盖；Vue 正确清理 watch 副作用并处理同样竞态。
- 增加 React Effect 清理实验与 Vue ref/computed 依赖实验；能解释每次执行原因。
- 两框架各有一个失败先复现、修复后通过的测试。

G3-I1，20 分钟：“为什么管理台看见了旧订单？从 UI、请求、数据库、缓存分别提出能证伪的假设。”追加 React/Vue 更新机制对照，不仅复述 API。

## 6. G4：身份、安全与数据权限

能力：S01/S02、J06。依赖：G1 最小身份、G2 数据所有权、G3 查询范围。

| 题号 | 笔试题 | 判分要点 |
| --- | --- | --- |
| G4-W1 | 登录成功且前端隐藏了按钮，为什么仍不能证明授权正确？ | 服务端逐资源/租户校验，水平与垂直越权；列表过滤和写入条件都要覆盖 |
| G4-W2 | OAuth2、OIDC、JWT 各是什么，CORS 能防 CSRF 吗？ | 授权框架、身份层、令牌格式分开；CORS 不是鉴权，Cookie 自动发送仍要 CSRF 防护；JWT 默认非加密 |
| G4-W3 | 文件上传为什么不能只看扩展名？服务抓取用户 URL 有什么额外风险？ | 类型/大小/内容/路径/访问控制；隔离存储；SSRF 内网/重定向/地址解析与出网约束 |

G4-P1：建立两个租户、两种角色、各自订单；上传只用合成文件，攻击仅限授权实验环境。

- 匿名、非拥有者、跨租户、权限撤销均有拒绝测试；成功授权仍能正常使用。
- 参数化 SQL、输出编码、跨站防护、上传限制、回调验签/防重放分别至少一个负例。
- OIDC 接测试身份提供方，校验签名、issuer、audience、时效；不自制“签个 JWT 就完成登录”协议。
- 令牌/密钥不出现在仓库、客户端包和日志；审计能定位操作者但隐藏敏感值。
- 交付威胁表、权限矩阵、安全测试结果和适用合规清单。法律适用不能由实验成绩代替。

G4-I1，20 分钟：“用订单编号越权读到别人的数据，如何止损、定位影响和补回归？”追问缓存键、列表查询和日志泄漏。

G5-P1：围绕同一订单建立可执行回归矩阵。

- Java：单元不变量、真实数据库并发、接口契约、对象/租户授权。

- 浏览器 E2E 各跑一条关键用户路径；键盘可操作，焦点与错误提示可理解。
- 故意改失败字段名、移除授权条件，确认相应测试变红，再恢复代码；防止“绿但没有断言”。
- CI 测试失败不部署；依赖/镜像扫描有处置记录；最小测试环境可回滚，无真实敏感数据。

G5-I1，20 分钟：“发布频繁而 E2E 很慢，你如何分层、并行和治理不稳定测试？”追问不能靠无限重试隐藏偶发失败。

## 8. G6：排障与可测量的优化

能力：J02/J03、O01/O02、H01、F02、R04/V04 性能。依赖：G5 可重复测试、日志和数据基线。

| 题号 | 笔试题 | 判分要点 |
| --- | --- | --- |
| G6-W1 | 线程数翻倍、平均延迟下降就说明容量提升了吗？ | 下游/CPU/队列约束，成功吞吐、尾延迟、错误/拒绝；不能只看均值 |
| G6-W2 | 堆并没满却被容器杀掉，应该收集什么？ | 容器限制/退出原因、堆外/线程栈/本地内存、峰值；先区分 JVM OOM 与系统终止 |
| G6-W3 | React memo 与 Vue 编译提示能否保证页面更快？ | 前提、比较与缓存成本、动态依赖、测量；优化不影响正确性；框架不是性能保证 |

G6-P1：在隔离环境完成四个小实验，可分周完成。

- 前端：React 多余渲染或长列表、Vue watch/更新问题各一次；录制轨迹，修复后同条件复测。
- Java：线程阻塞/死锁/有界池饱和选一个；另做内存增长定位，区分线程与堆证据。
- 数据库：慢 SQL 或锁等待定位，保留执行计划、扫描量/等待与修改依据。
- 容量：按总方案负载规范做基线与阶梯压测；至少三次同条件运行，确认压测机不是瓶颈。
- 每次笔记含影响、时间线、假设、排除层、证据、修复、同指标复测、局限。转储脱敏，不对生产随意抓取大堆快照。

G6-I1，30 分钟故障桌面演练：“上线后 p99 变差，CPU 不高，数据库连接池超时。”分轮给证据，评分看提问和推理；必要时先回滚，不为了证明单变量拖延止损。

## 9. G7：微服务、分布式与高并发

能力：M01～M03、D04、H02、J06、R04/V04 SSR。依赖：G2 正确性、G4 安全、G6 观测与容量。

| 题号 | 笔试题 | 判分要点 |
| --- | --- | --- |
| G7-W1 | Outbox 消除了什么窗口？消费者在数据库提交后确认消息前崩溃会怎样？ | 业务与发送意图原子提交；投递/消费可能重复；去重与副作用同事务；外部效果需额外幂等协议 |
| G7-W2 | 网络分区、超时、租约过期后为什么不能简单说“操作失败”？ | 未知结果、客户端观察与提交分开；旧持有者仍可能执行，fencing 或条件约束；重试预算和查询确认 |
| G7-W3 | Next.js 服务端组件与 SSR 是一回事吗？Vue SSR 为何不能跨请求共用可变用户 store？ | RSC 与 HTML 渲染关注点不同；水合/客户端交互边界；服务端请求隔离，避免用户数据泄漏 |

G7-P1：保留模块化单体版本，再拆订单与通知/履约两个独立部署服务；数据所有权不共享写表。

- 比较拆前后的部署、延迟、失败和成本，提交 ADR；即使业务决定不拆，也需完成两进程教学实验。
- 使用 Outbox 和一种 MQ，验证重复、乱序、消费者重启、毒药消息、积压/重放与补偿失败。
- 下游故障时有超时预算、退避/抖动、熔断或限流；拒绝不能误画成成功，重试不能导致持续放大。
- 高并发抢购/预约：增加负载仍无超卖/重复业务效果；过载时有明确拒绝与恢复，不只比 QPS。
- Next.js 与 Nuxt 各做一个小型 SSR 页面，测试两个并发用户的数据隔离和水合；解释缓存边界。
- 消息去重保留期、对账补偿、契约兼容分别有说明；不声称“上 MQ 就恰好一次”。

G7-I1，40 分钟：“为库存紧张的预约系统设计方案，随后加上服务超时、重复支付回调和跨地域读取约束。”要求容量估算、数据归属、失败语义、替代方案；支付用模拟回调。

## 10. G8：发布、观测与恢复

能力：C01/C02、O02、S02。依赖：G5 最小部署、G6 指标、G7 多服务契约。

| 题号 | 笔试题 | 判分要点 |
| --- | --- | --- |
| G8-W1 | readiness 和 liveness 能否用同一项数据库检查？ | 接流量与重启目的不同；下游故障不应引发全体重启风暴；startup 处理启动 |
| G8-W2 | 应用回滚为何不一定能回滚删列迁移？ | 数据不可逆、旧应用兼容；先扩展再收缩、恢复另计划；不能直接自动执行反向 SQL |
| G8-W3 | RPO/RTO 怎么验证？有备份文件就算完成吗？ | RPO 是可容忍的数据丢失窗口，RTO 是恢复时间目标；真实隔离恢复、完整性核对、记录实测，不能靠文件存在判断 |

G8-P1：部署一个测试环境，域名/TLS、服务、数据库、对象存储、观测和权限均标注清楚。

- 容器最小权限、运行时密钥、数据库私网访问；本地模拟替代真实云时记录未验证部分。
- Helm 或 Terraform 至少一项可重放；环境参数与秘密分离。
- 测试失败阻止发布；一次滚动或灰度及回滚，调用方连稳定服务地址。
- 延迟/错误/资源看板；SLO 明确分子、分母、窗口；告警触发与恢复通知均验证。
- 完成一次负载测试、一次故障注入、一次备份恢复，三者不能互相替代。
- 练习默认恢复目标可设 RPO <= 5 分钟、RTO <= 30 分钟；需有相应日志/备份方案并实测。环境不支持时先声明新目标和原因，禁止事后改目标伪装通过。
- 云资源设预算、生命周期和清理步骤；恢复在隔离实例进行，不覆盖唯一数据副本。

G8-I1，30 分钟：“发布后出现 5xx，回滚应用仍失败，你如何止损、沟通、判定是否恢复数据？”追问权限、可观测性、成本及数据丢失上限。

## 12. 复习、诊断和题库扩展

1. 第一次尝试记录错误类型：概念、实现、证据、表达、先修；推荐一条修复任务，不推送整章重学。
2. 通过后约 1/7/21 天可选短回忆或变体题，时间只是提醒建议；不因未签到取消进度。
3. 每四周轮换一项算法、一项框架、一项系统问题；题型按能力覆盖，不循环同一答案。
4. 完整题库下一步为每个核心单元补“基础、故障、迁移”三类变体，经过试做校准难度；当前这些题是首批可执行规格，不是穷尽题库。
5. 任务上线须补齐输入数据/脚手架、启动命令、正例、故意失败例、测试、参考实现、评分边界与版本，不允许只有“完成一个高并发项目”。

### 一份反馈示例

任务 `G2-P1`：同键重试出现两条订单。

- 观察：并发请求后业务行数为 2，期望为 1；测试环境与报告附在当前尝试。
- 已完成：HTTP 错误结构、单请求事务测试通过，这些结果保留。
- 下一步：先检查业务幂等键的唯一约束及去重与副作用的事务边界。

- 复测：只重跑相关并发/幂等用例，再运行完整回归；不把整关归零。
