## 数字先写死

- **10 万**：峰值〔QPS｜每秒请求数〕或同时在途请求。卷面上要声明是哪一种。
- **一百万**：注册用户，不是同时在线。
- **50 倍**：相对平日峰值，不是相对注册用户。
- **超过 3 秒**：这一条语句的耗时。先分开执行时间和锁等待。
- **秒级**：副作用和读模型允许旧多久。不是库存可以晚几秒再守。

## 架构图必须有的框

1. 客户端。
2. 接入：负载均衡或网关，限流标在这一跳。
3. 无状态下单服务，可以水平加副本。
4. 同步边界：同一数据库事务里的幂等键唯一约束、库存条件更新（`UPDATE` 带库存条件，影响行数是 1 才继续）、订单行。
5. 异步边界：〔Outbox｜事务发件箱〕→ 消息 → 消费者（通知、检索、履约）。投递至少一次，消费端按业务键幂等。
6. 读路径：允许滞后的从库或缓存，写明允许旧几秒。
7. 容量数字：平日峰值、50 倍后的峰值、削峰后数据库实际承接的写入速率。
8. 失败时用户看见成功、失败还是等待。

不合格：只画微服务框；把缓存扣减画成库存权威；用「五千万行」直接引出拆库。

```text
客户端
  → 接入（限流：超过则排队或拒绝）
  → 无状态下单服务（按峰值加副本）
  → 数据库事务：幂等键唯一约束 + 库存条件更新 + 订单行
  → Outbox → 消息 → 消费者（通知 / 检索 / 履约，至少一次，消费幂等）

读路径（旁路）：从库或缓存，标注允许旧 N 秒
```

## 场景要点（阅卷）

**50 倍。** 无状态副本按峰值加。入口限流，超过的排队或拒绝。用户必须当场知道的库存结果仍是条件更新。静态页不打到下单库。被限流后无限重试会放大洪峰。

**五千万行连表超过 3 秒。** 题面 SQL 没有 `user_id` 等值，条件是 `status IN ('paid', 'shipped')` 和 `u.level = '500'`，再按时间取 20 行。五点都是可能原因，用慢日志和 `EXPLAIN ANALYZE` 确认。优化索引是 `(status, created_at, id, user_id)`：`id` 紧跟 `created_at`，否则主键被补到末尾后，`ORDER BY created_at, id` 用不上。两个状态各写成等值，`level` 字面量与列类型一致，`UNION ALL` 后再 `LIMIT 20`。不能先取 20 行再过滤等级。`EXPLAIN` 里 `orders` 是驱动表，`users` 是 `eq_ref`，且没有对整个状态做 filesort；驱动表错了再用 `STRAIGHT_JOIN`。`level = 500` 的用户很少时，才改从 `users.level` 出发。行数本身不是拆分开关。

**`status IN (...)`。** 等值的 `user_id` 在组合索引左边，`status` 在右。`IN` 可以按多个范围用索引。`status` 取值少，单独索引它，优化器仍可能扫很多行。不带用户、按状态扫全表的报表不要跑在下单主库的在线事务上。

**状态频繁变更。** 〔二级索引｜聚簇索引之外的索引，叶子里存主键〕里包含 `status` 时，每次改状态都要删旧条目、插新条目。某一个用户的查询留 `(user_id, status)`。没有 `user_id`、按时间取最近若干行的查询另留 `(status, created_at, id)`。只给报表用的宽索引不要把常改列放最左。历史状态另表。在线要用的索引不能为了少维护就拿掉。

**秒级延迟。** 同步返回接受、拒绝或等待。通知和履约走 Outbox。读模型写明允许旧几秒，积压里最老一条的年龄要落在这个预算里。把扣库存改成只发消息，窗口里会超卖。刚写的订单只读滞后从库时可能暂时读不到，要读主库或明确仍在处理。
