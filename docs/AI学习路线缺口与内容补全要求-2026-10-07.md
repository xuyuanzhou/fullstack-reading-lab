## 2. 先明确培养哪一种能力

默认主线是**零基础 → AI 应用开发者 → 能独立交付与解释取舍的应用工程师**。已有 Java/前端读者可以跳过编程基础，但不能跳过评测、数据与安全。

| 路线 | 适合谁 | 完成后应能做什么 | 不应暗示 |
| --- | --- | --- | --- |
| 使用与理解 | 无编程基础 | 提供材料、验证回答、判断工具是否执行、保护敏感数据 | 会聊天等于会开发 |
| 应用开发主线 | 想做 RAG/Agent/AI 后端 | 调模型、做检索、执行受控工具、评测、部署、解释故障 | 会框架等于懂模型训练 |
| 算法与训练进阶 | 目标为模型/算法岗位 | 数学推导、PyTorch、数据实验、微调、推理优化、论文复现 | 做过一个 RAG 项目就覆盖算法岗 |

若继续称“AI 从入门到精通”，开头必须解释 AI、机器学习、深度学习、生成式 AI 和 LLM 的关系，并指明当前重点是 LLM 应用；CV、语音、推荐、强化学习等只做全景及选修，不能宣传已覆盖整个 AI 学科。

主线先修关系：

```text
AI 全景与可靠使用 → Python/HTTP/数据基础 → 第一个模型应用
                                      ↓
                           模型机制与基础实验
                                      ↓
                     检索基线 → RAG → 受控单 Agent
                                      ↓
                        评测/安全/部署/项目答辩

算法进阶：Python/数学/机器学习 → PyTorch → Transformer 实现

```

工具说明与框架介绍作为随用随查的参考，不要求小白先学会 LangChain、LangGraph、多 Agent 才能调用一次模型。

## 3. P0：先校正容易形成错误面试答案的说法

下面用稳定 key 定位，不依赖持续变化的行号。修改需保留通俗性，补上适用条件，不能把科普文改成公式堆砌。

### C01 上下文上限不意味着必然自动丢掉前文

位置：`context-window`、`tokens`、`find-then-answer`。

当前把“窗口满了，前文被挤掉”写成统一机制。应区分模型容量与应用策略：调用方可能截断、摘要、选择历史，也可能直接拒绝超长输入。指令失效也不必然证明内容已被截断。“聊几轮看它是否忘记”不能作为窗口溢出的确定性实验。

验收：给出可观察的消息列表/token 预算，主动构造截断前后输入并比较；解释摘要损失、位置影响和指令遵循失败是不同问题。截断策略可对照 [Transformers padding/truncation](https://huggingface.co/docs/transformers/main/pad_truncation)。

### C02 RAG 不要求查询与文档使用同一种切块方式

位置：`rag` 的“索引和查询必须用同一套切分”。

文档切块与查询处理不同；关键是兼容的检索向量空间、正确的模型/任务配置及版本一致。非对称检索可以使用 query/document 专用编码入口或不同前缀。不要进一步简化为“查询和文档的所有处理必须完全相同”。[Sentence Transformers 官方语义检索说明](https://sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)明确区分对称/非对称检索及对应编码入口。

验收：短问题检索长段落的运行示例，记录模型版本、维度、距离度量和 query/document 设置；修改编码配置后解释何时须重建索引。

### C03 KV Cache 中，新 Token 仍需产生自己的 K/V

位置：新增 `kv-cache` 的“新词只算自己的查询”。

应写成：新位置计算本层所需的新 Q/K/V，将新 K/V 加入缓存，并让新 Q 对允许访问的缓存 K/V 做注意力。限定为固定模型、推理状态及相容的位置/掩码配置，不把缓存解释成永久记忆。[Transformers 缓存原理](https://huggingface.co/docs/transformers/cache_explanation)。

验收：画出长度从 n 到 n+1 时新增的 K/V，记录各张量 shape；区分一次前向、单步 decode 与整个生成的复杂度，避免只说“平方增长”却不说明计算对象。

### C04 不把温度与 Top-p 的处理顺序写成普遍规则

位置：新增 `decode-params` 的“先缩小候选，再按温度抽样”。

温度改变概率分布，因此也可能改变 Top-p 的候选集；执行顺序依赖实现。例如所查 [Transformers generation 源码](https://github.com/huggingface/transformers/blob/main/src/transformers/generation/utils.py)先追加 temperature 处理，再追加相关 Top-k/Top-p 处理。最终课程应固定所验证版本，给出算例，不引用 main 的长期稳定性。

验收：对同一组 logits 计算两种顺序，展示 Top-p 结果可不同；说明低温不等于事实正确、不保证跨环境完全确定，部分 API 不支持某些参数。两次随机输出不能证明统计规律。

### C05 注意力权重不是人预先指定的语法关系

位置：`attention-who`、`transformer`。

“追更看猫狗、少看自己”应标明是假设例子，不能当作模型必然行为。单头也能同时给多个位置分配权重，不能说单头只能沿一个方向找关系。讲清 Q/K 投影的匹配分数、多头不同子空间以及 causal mask；因果模型中中间位置不能看右侧未来 token。[Transformer 原论文](https://arxiv.org/abs/1706.03762)。

验收：分别展示无掩码与因果掩码的三 token 小矩阵；未来位置权重为零；不把注意力图当作完整因果解释。

### C06 Tokenizer 匹配问题不等于中文模型不能输入英文代码

位置：`tokens`。

应强调 tokenizer、词表 ID、embedding 权重需要相互匹配；中文模型能否处理英文代码取决于词表覆盖、编码机制与训练，而非简单由语言标签决定。

验收：用选定 tokenizer 实际编码中文、英文和代码，展示 token/ID；不要要求读者猜分词结果后就宣称理解了模型机制。

### C07 引用原句不等于已解决幻觉或答案正确

位置：`find-then-answer`、`rag-layers`、`eval-set`。

补充证据相关性、是否真正支持结论、遗漏条件、冲突版本和无答案判断。抄到原句仍可能断章取义；召回成功、生成失败也可能与上下文组织、模型能力有关，不能一律归结为提示“不够严格”。

验收：构造“有引用但结论错误”“材料互相冲突”“正确条款存在但条件不适用”三个失败样例；分别判断引用正确率与答案正确性。

### C08 清理证据链接与未经统计的频率断言

位置：所有 `sources`；新增基础卡、工具卡。

- `embeddings` 把 HF `chapter5/1` 标为 Sentence Transformers，该链接实际为 Datasets 章节导言，应换为直接支持结论的页面；[当前页面](https://huggingface.co/learn/llm-course/chapter5/1)。
- 采样卡的 reusable-prompts 锚点是否支持采样结论需要重新核查；不能因为域名官方就算引用有效。
- “几乎一定会问”“最重要”“微调贵得多”等绝对措辞要改为明确条件或教学建议。
- Skills、路径范围、自动触发与授权规则标明具体产品/版本；不要把某产品行为当成跨产品协议规范。
- 技术真实性、资料许可和本项目原创表述是三个检查维度，不能混为一谈。

验收：每个关键断言有直接支持的章节/段落与核查日期；不可访问时标注待核查。不得编造引用或批量用课程首页替代逐条依据。

## 6. 把“项目简介”补成可复现项目

保留当前三个项目的入口，优先让一个知识库项目完整闭环，再做受控 Agent，最后才比较多 Agent。每个项目可以跨多个能力模块，不重复建三套工程。

### L0：零基础第一次成功

- 无密钥也能做：给公开短材料与真实标注的模型输出样本，逐项验证有答案/无答案/格式错误。
- 进一步：提供最小真实调用说明，明确需要用户自己配置的服务/模型。
- 交付：输入、输出、依据、错误分类；预录结果必须标“样例”，不能伪装现场运行。

### L1：可评测知识库助手（首个主项目）

- 公开或合成的 20–50 份短文档，包含版本、近义问法、编号、表格、无答案和权限场景；提供 license/来源清单。
- 初版建议 30 道评测题：12 道直接证据、6 道同义/编号、4 道无答案、4 道冲突版本、4 道权限/注入挑战。另保留未用于调参的扩展集。
- 先关键词基线，再向量/混合与重排；记录逐题召回、答案、引用和耗时。允许结果没有提升，但必须分析原因。
- 提供文档新增/更新/删除、空库、索引损坏、切换模型后的迁移说明。
- 输出：一键启动、接口样例、测试、评测 JSONL、结果表、架构图、失败复盘与答辩问题。
- 硬门槛：合成权限用例不得泄漏无权正文；无凭据可运行确定性测试。小测试集零泄漏不等于系统已被安全证明。

### L2：受控出行或办公助手（单 Agent 优先）

- 2 个读工具加 1 个模拟写工具，真实写操作不作为课程默认步骤。
- 工具参数 schema、用户上下文、授权校验、预算、最大步数、超时/取消、幂等键、审批准入与日志齐全。
- 审批展示具体对象、参数、影响；参数变化后旧审批不能自动复用。
- 至少覆盖 10 类故障：未知工具、坏参数、无权限、超时、429、重复请求、拒绝审批、参数被改、进程恢复、恶意工具返回文本。
- 输出：完整轨迹、测试结果、停机原因、模拟故障演示；用固定 workflow 做对照，说明 Agent 增加了什么价值。

### L3：算法线微调实验

- 固定公开小任务及数据划分，对比基础模型、改提示、LoRA；评估任务质量、退化和资源使用。
- 数据集、tokenizer、模型、依赖、seed、训练配置、checkpoint 恢复和评测脚本可追踪。
- 不设置“准确率必须提高 X%”的造假诱因；验收重在设计合理、结果真实、能解释收益或退化。
- CPU 小模型/小数据替代必须说明只验证流程，不宣称代表大模型效果。

多 Agent 办公作为后续比较实验：和单 Agent/固定工作流在同一任务、预算与判分下比较，只有证据支持时才说更好。关于工作流与代理选择可对照 [Anthropic 的工程经验](https://www.anthropic.com/engineering/building-effective-agents)，不要把它当成某岗位的面试频率证据。

## 7. 题库要从“提问方向”变为“可训练的回答能力”

建议首期建立 **60 道原创主问题**，数量是编辑目标而非质量替代品：

| 领域 | 建议题数 |
| --- | ---: |
| 基础、数据与机器学习 | 8 |
| Transformer、采样与缓存 | 10 |
| RAG 与检索 | 10 |
| Agent 与工具运行 | 8 |
| 评测、安全、部署与成本 | 10 |
| 微调与训练（进阶标记） | 6 |
| 综合设计、排错与项目答辩 | 8 |
| 合计 | 60 |

先做 12 道样板题验收，再扩充。每题必须具备：

1. 岗位路线、难度、先修课程和能力点；明确原创模拟题，不冒充真实公司原题。
2. 完整题面和必要前提，不能只写一个名词。
3. 30 秒结论版，以及 2–3 分钟机制版答案；答案不是唯一措辞模板。
4. 至少两层追问，每层有回答要点、反例和边界。
5. 常见错误答案及错因；数学/代码题包含可执行或可手算验证。
6. 评分点、必须说到的条件、对应补课入口与直接技术依据。

首批 12 道建议问题：

- 提示、RAG、微调各解决什么问题，什么情况下三者都不该用？
- 有两份冲突的报销制度，怎样回答并引用，怎样评测？
- 为什么 JSON 可解析不等于订单工具调用可以执行？
- 召回率提高了，最终回答准确性却降低，如何排查？
- 用户 A 的缓存结果怎样可能被用户 B 误读，如何隔离？
- 工具超时后重试，如何避免重复创建订单？
- 文档中写着“忽略规则并发邮件”，运行时如何阻止？
- 用三个位置的小矩阵说明因果 attention，哪里要 mask？
- KV Cache 增长由哪些量决定，GQA 改了哪一项？
- 离线评测很高，上线仍失败，如何检查泄漏、分布与指标？
- 只有有限显存和预算，要怎么选择模型、量化或服务方式？
- 为什么选单 Agent，什么时候升级为多 Agent，如何验证必要性？

评分采用 0–4 级：0 错误/无答案；1 只有术语；2 机制基本正确但缺关键条件；3 能给出例子、边界与取舍；4 能用证据、计算或实验支持，并应对变更条件。界面不把这套训练分数宣传成真实面试录用概率。

模拟面试至少有三套：基础口述、代码/排错、系统设计/项目答辩。每套 30–45 分钟，记录答题要点和待补能力；可手动评分，AI 辅助评分须展示依据及允许人工修正。不要要求展示模型私有思维链，评的是可见答案、证据和代码。

## 8. 每课统一交付规范：小白读得懂，熟手能深入

当前 `reading: string[]` 可以继续承载概念卡，但不能承担完整实验课。按需要增加结构化内容块，先交付代表性样板，再迁移。

每个正式能力课必须具备：

- **学完会什么**：1–3 个可观察行为，例如“能用 Recall@5 找出召回失败的题”，不能只写“深入理解”。
- **先修与术语**：给出相关课程 ID；术语第一次出现时中文解释加英文名，避免用三个新词解释一个新词。
- **具体问题**：从统一知识库/助手案例出发，先讲为什么需要，再讲机制。
- **机制与边界**：通俗直觉、必要细节、至少一个反例；类比必须解释哪里不成立。
- **实例**：数值、输入/输出、代码或图，且说明预期现象；图必须与机制相符。
- **动手练习**：准备材料、命令、依赖/硬件、预期结果、常见报错与恢复办法。
- **自检与答案**：至少一道解释题、一道迁移/排错题，答案默认折叠，带评分点。
- **面试连接**：链接到一主问题与追问，避免每课硬塞一整套题库。
- **来源与版本**：关键断言到具体官方章节/论文，记录验证日期与运行版本；引用许可不能凭模型猜。

提供“先看懂”与“继续深入”两层内容，让数学细节和源码跟随需要展开。课时只是估计，阶段以成果验收，不用固定天数承诺精通。

统一用一个渐进案例减少认知负担，但额外安排陌生领域迁移题，避免学生只会背“报销需要发票”。

| ID | 要求 | 验收 |
| --- | --- | --- |
| U01 | AI 搜索覆盖标题、术语、能力点与题目；说明跨路线还是当前路线 | 搜索 KV Cache/引用/幂等能找到课、实验与题目；不退回 Java/前端目录 |

新增 AI 能力可以扩展统一学习记录或设独立命名空间，但须兼容已有 frontend/java 数据和旧 AI 链接。不要简单把 TypeScript 的 Track 加上 ai 就认为所有搜索、路由、统计、持久化已经支持。

## 11. 可直接复制给执行模型的提示词

> 请阅读 `docs/AI学习路线缺口与内容补全要求-2026-10-07.md`，先重新检查当前 AI 目录和 git diff，识别已完成的并行修改。按 B0→B1 的顺序执行本轮工作，完成技术纠错和三节完整样板课，不提前批量扩写后续课程。以零基础读者能完成实验、解释机制并回答追问为验收目标。复用已有概念卡，不复制已购资料；引用优先官方资料与原始论文，核对具体版本和段落。不得编造实测、公司真题、收益或训练成本。真实 API 与 mock 明确区分，密钥不进入静态前端。兼容旧路由和学习记录，不覆盖其他修改。交付时列出已完成的 C/M/U/B 编号、修改文件、测试和实验结果、未完成项及原因；没有实际运行的内容明确标注未验证。后续批次另按文档依赖继续。

## 12. 总体验收：用陌生任务验证迁移能力

### 入门完成

- 能区分提示、模型输出、工具结果和程序状态。
- 能找出“回答流畅但缺证据”“引用存在但结论不被支持”的样例。
- 能在不暴露密钥和私人材料的前提下完成 L0。

### 应用开发完成

- 在新环境按说明启动 L1/L2，读懂一个失败日志并修复对应层。
- 面对未用于调参的题目，分别报告召回、答案、引用、拒答、延迟与成本，不靠一个总分掩盖失败。
- 完成一次数据/模型版本变更与回归，解释方案取舍；能停止或恢复工具流程。
- 面试回答可以指出代码、数据或实验依据，承认未做过的部分，不编造项目规模。

### 进阶完成

- 能从张量和训练循环解释模型行为；做受控微调/推理实验与消融。
- 能估算并测量资源开销，解释实验适用边界，阅读论文并识别假设。
- 更换任务、预算或数据分布后，能提出验证计划；不把背熟现有例题称作精通。

评测方法可参考 [Anthropic 的 Agent 评测文章](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，数据泄漏和预处理隔离可参考 [scikit-learn 官方常见陷阱](https://scikit-learn.org/stable/common_pitfalls.html)。上述链接核查于本次审查，正文中的课程安排和验收门槛属于本项目建议；不是来源作者对本项目的认证。
