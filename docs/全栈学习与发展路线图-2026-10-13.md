## 2. 学完意味着什么

不承诺“从容应对所有面试题”或“学完获得高级头衔”。培养目标是能处理主流业务场景、解释机制、证明正确性，并能面对陌生问题提出验证方案。

统一能力尺度，应用于每个知识单元：

| 等级 | 可观察行为 |
| --- | --- |
| 0 未验证 | 未做或只有已读记录 |
| 1 能解释 | 说清概念、适用条件与一个反例 |
| 2 能实现 | 在有限提示下完成正常和异常路径 |
| 3 能独立验证 | 独立完成测试、定位问题、复测，说明取舍 |
| 4 能迁移 | 面对新约束修改方案，并用实验或生产证据解释效果 |

完整路线要求全部必修单元至少达到 3；Java、React、Vue、数据正确性、分布式、高并发、排障各完成至少一项等级 4 挑战。这里“精通”是持续提高的能力目标，不是刷完一次题的永久认证。

阶段成果：

- 第三关：可运行的读写原型，不等于可上线。
- 第五关加最小部署：有安全与测试证据的应用交付，适合开始岗位定向训练。
- 第八关：具备分布式实验、容量、运行、恢复证据。
- 第九关及全矩阵达标：完整全栈作品与设计答辩材料；架构师还需真实团队的长期决策结果。

## 4. 技术选择与版本策略

1. 主工程选 Java + Spring Boot + MySQL + Redis；React 用户端、Vue 管理端共用契约。只有实测需要时接 MQ、搜索和服务拆分。
2. React 与 Vue 各自有框架生态，不把 Next.js 当 React 本体，不把 Nuxt 当 Vue 本体。SSR 小实验两边都做；生产主项目只选实际需要的渲染方式。
3. Java 21 可作为统一实验基线；新 JDK 的虚拟线程实现、预览功能单独记录。Boot、Cloud、Security、JDK 依赖按官方兼容矩阵选择，不把某一补丁版永久宣称“最新”。
4. React 19 系列和 Vue 3 系列作为教学方向；开班时锁定已验证小版本、Node 受支持版本、包管理器与锁文件。Nuxt/Next/Router 缓存和路由 API 按该实验版本核验。
5. Hystrix/Ribbon/Zuul 1、Vue 2、旧 React 生命周期等用于遗留维护题；不作为新项目默认。新旧栈对照是迁移能力，不以背旧实现代替现代机制。
6. 通用能力必修，工具按代表实现。不能要求同时部署 AWS/阿里云/腾讯云，或同时精通所有 MQ/NoSQL/网格产品。
7. 趋势分级：虚拟线程、服务端渲染/组件、供应链安全、可观测性列入相应必修；AI 应用、Serverless、微前端、GraphQL/gRPC、Service Mesh（服务网格）、eBPF 系统观测按岗位选修。选修不代表这些技术没有价值。

## 8. 排障与性能实验规范

### 8.1 先区分生产处置与学习实验

生产：确认影响与安全边界 -> 通知负责人 -> 必要时回滚/降级/限流止损 -> 保存可行证据 -> 定位 -> 修复 -> 复测 -> 复盘。实验：固定条件 -> 一次改一个可解释变量 -> 对照复测。不能把“一次只改一层”当作禁止生产紧急止损。

| 故障 | 首批证据 | 判定与验收 |
| --- | --- | --- |
| 页面卡顿/旧响应覆盖 | 网络瀑布、长任务、组件渲染轨迹、请求顺序 | 分清服务慢和主线程忙；取消/忽略旧响应，交互不回退 |
| CPU 高/线程池满 | CPU profile、线程状态、队列/拒绝数、调用栈 | 指到计算、锁竞争或排队，不直接加线程 |
| 内存增长/被杀 | 堆/堆外、GC 日志、容器退出原因、引用链 | 区分泄漏、峰值、限制；提供稳定运行对照 |
| SQL 慢/死锁 | 慢日志、执行计划、锁等待、事务时间线 | 在同等数据和负载下复测；恢复不变量 |
| MQ 积压/重复 | 消费延迟、最老消息年龄、重试次数、幂等记录 | 故障恢复后可排空；无重复业务效果 |
| 网络/证书/代理失败 | DNS、连接、TLS、超时预算、代理/应用日志 | 指明失败位置；不通过关闭证书校验解决 |
| 发布后错误/数据损失 | 版本、指标变化、迁移记录、恢复日志 | 应用回滚与数据库恢复分开；兼容性经验证 |

### 8.2 固定负载，不追逐脱离环境的数字

每份压测报告声明 CPU/内存、实例数、版本、数据量、索引、冷热缓存、请求比例、到达率、并发、预热、持续时间、重复次数、压测机资源。推荐从 10 万条合成订单、读写比例 8:2 开始；这是练习数据，不是行业标准。

先记录基线，再测试阶梯、突发、持续负载和下游故障。统计成功吞吐、错误/拒绝、p50/p95/p99、CPU/内存、池/队列、数据库/缓存/MQ。至少三次可比运行；说明采样、噪声与协调遗漏问题，不用平均延迟掩盖尾延迟。

优化成功要求：正确性测试通过，目标指标在预先声明的条件下改善或解释无改善，且没有把问题转移为错误、丢数据或超预算。硬件较弱可缩小负载，不能把本地结果宣称百万并发。

前端可参考真实用户第 75 百分位的 LCP <= 2.5s、INP <= 200ms、CLS <= 0.1；来源见第 11 节。实验室报告必须标注环境，不能用一次 Lighthouse 分数声称已达到真实用户指标。

## 9. 考核与岗位适配

| 企业应用 | 权限、审计、工作流、集成、报表、遗留迁移 | 测试、接口兼容、部署与可维护性 |

求职前选 10～15 份目标岗位描述建立差距表，按地区、级别、业务分组；未调查前不写“所有公司必考”。每四周更新一次，遇到未知工具映射到已学能力，再做小型验证。
