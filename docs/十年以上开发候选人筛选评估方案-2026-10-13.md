# 十年以上开发候选人筛选评估方案

| 字段 | 内容 |
| --- | --- |
| 日期 / 状态 | 2026-10-13；筛选方案完成，尚未收到候选人材料、开展面试或背调 |
| 核心门槛 | 经核实的软件开发实战经历达到 10 年及以上，不能以高分抵消年限不足 |
| 适用 | 资深软件工程师、核心系统技术负责人；具体职责在启动时固定 |
| 项目关联 | [实施总计划](./全栈学习平台实施总计划-2026-10-13.md) 的人员配置，不是 AI 模型选型 |
| 配套产物 | [候选人名单与能力报告模板](./候选人名单与能力评估报告模板-2026-10-13.md) |
| 结论边界 | 提供有证据的评估建议，由招聘负责人作最终决定；不保证完全消除履历失实风险 |

## 1. 评估原则与启动条件

目标不是寻找“会讲十年故事”的人，而是验证持续的软件交付经验、真实责任、可复现技术能力与协作行为。

启动前固定岗位说明：实际业务、主要技术栈、编码/架构/管理占比、需要承担的生产责任、工作地点和必要工作条件。评分与题目版本在首位候选人面试前冻结，不因人调整标准。

本项目的 E1 偏 React/TypeScript/Vue 与平台工程，E2 偏 Java/数据/分布式实验。二者都用本方案的年限与通用能力门槛，但按岗位选择编码题；不能因 E2 不熟悉某个 UI 库就断言其没有十年开发经验。招聘“全栈技术负责人”时再明确要求跨端设计深度。

不以年龄、毕业年份、性别、婚育、健康、籍贯、学校/公司名气等替代实战能力。工作空档不作为负面人格判断。合理安排辅助技术、语言澄清或等价考试条件，仍使用相同技术标准。

需要的初始材料：

1. 候选人编号、脱敏简历，经历起止时间及全职/兼职等实际投入形式。
2. 两个代表性中大型项目说明，至少一个覆盖需求到上线、运维与后续演进；单个长周期系统可提供两次独立的重要交付。
3. 至少一个本人主导核心架构设计并落地的案例，说明决策权、个人修改、协作人与结果。
4. 两个不同层面的复杂问题案例，其中至少一个生产排障或性能调优案例。
5. 可披露的证据索引，以及是否同意进一步核实经历的授权范围。

材料不完整先标“待补证”，不直接视为造假。不能要求身份证、完整社保/薪资、私人账户、原公司源码或客户数据作为默认材料。

## 2. 十年实战经验核验

### 2.1 统一统计口径

本方案默认累计有效软件开发实战经历不少于 120 个月，不要求连续十年。以评估日为截止，不把未来月份计入；“2016 年至今”不能直接视为已满十年。

有效经历是承担具体软件设计、编码、测试、上线、运维改进或技术演进责任的工作，包括可核实的雇佣、合同、创业或持续项目工作。只有培训、刷题、课程观看，或纯行政管理而没有技术交付责任的时间不计入。技术管理岗位不能只因不每天写代码就一律剔除，需核对技术责任；当前编码能力另考。

统计规则：

- 对所有有效经历按时间去重；同一月份同时做两个项目不计两个月。
- 整个自然月持续承担开发职责计 1 个月，正常在职休假不另扣；部分月份按该月有职责的日历天数占比计算。
- 兼职经历单列；需折算时，先约定统一、可验证的投入比例，同日有效比例合计最多为 1。无法合理确认的比例列待核实，不擅自假定全职。
- 累计值保留原始精度，达到 120 才通过；不能把 119.8 四舍五入成 120。
- 只有月份没有日期时计算保守下界和可能上界；若门槛落在两者之间，补日期或证明，不能猜测通过。
- 对“已核实”“仅陈述”“有争议”的时段分别统计；仅已核实的保守累计达到 120 个月，才能标门槛通过。

边界检查：无重叠的完整 120 个月通过年限门槛；120 个月中有 6 个月重复计入，去重后 114 个月不通过；119 个月加一个时间不清的月份为待核实。这些是规则例子，不是任何人的评估结果。

### 2.2 核验方法

| 核验对象 | 要问清什么 | 可接受的核验方式 |
| --- | --- | --- |
| 时间线 | 开始/结束、重叠、空档、投入形式 | 候选人同意提供的脱敏任职证明、合同关键日期、交付记录或授权证明人核实 |
| 开发职责 | 写/设计/测试/上线/排障过什么 | 交付物索引、设计/评审记录、具体技术追问；职位名称不能代替职责 |
| 个人贡献 | 本人负责与他人负责的边界 | 现场重建决策、实现细节、失败复盘，必要时授权同事/主管核实 |
| 架构主导 | 谁提出方案、谁选择、谁推动迁移 | ADR/RFC 等脱敏决策材料、实施阶段、替代方案、本人责任及可验证结果 |
| 业务结果 | 指标定义、测量条件、上线影响 | 脱敏指标或区间、发布/复盘记录；不能披露时明确证据局限 |

采用组合证据，不要求每个人都有公开 GitHub。私有 Git 贡献图、证书或面试表现本身不能独立证明十年时间线。任职证明也只能证明其中的任职事实，仍需核对开发职责。

由招聘协调人核日期，技术面试官核职责，二者共同复核累计表。背调须事先取得授权，按授权范围联系证明人，不擅自联系现雇主、不搜索无关私生活。

候选人可对时间线和事实提出更正。重大不一致先请其解释；只有经过复核的虚假陈述才记录为诚信问题，拒绝披露保密资料不等于不诚信。

## 3. 硬门槛与名单规则

| 编号 | 门槛 | 必需证据 |
| --- | --- | --- |
| H1 | 已核实有效开发经历 >=120 个月 | 去重时间线、核验方式、复核记录 |
| H2 | 中大型项目全生命周期经验 | 两个代表案例或同一长周期系统的两次重要交付；至少一个完整生命周期 |
| H3 | 主导核心架构并实际落地 | 至少一个有本人决策、实施、上线和结果的核心系统案例 |
| H4 | 当前实际编码与复杂问题处理达标 | 现场编码、变更题、调试记录、对应分项分数 |
| H5 | 系统调优与团队协作达标 | 调优证据、协作行为访谈/评审模拟、对应分项分数 |
| H6 | 关键事实和核验程序完整 | 未决事实已解决或明确不影响门槛；授权、两名评估者意见、人工确认 |

合格名单仅纳入：H1～H6 全部通过、总分 >=80/100、所有能力分项达到其满分的 70%，且两位评估者完成复核的候选人。

状态必须区分：

- 待评估：尚未完成该流程。
- 待补证/复测：证据不足或有未解决冲突，不能进入合格名单。
- 不符合年限门槛：已确认少于 120 个月，注明仅针对当前岗位。
- 能力未达本岗要求：年限达标但明确未通过某项能力门槛。
- 合格建议：所有条件通过，提交招聘负责人作决定，不自动等于录用。

材料缺失不用零分代替，记“未评估”；不能将不完整报告算平均分排队。没有候选人资料时只能提供空白模板，不能生成名字或声称已筛出零名合格者。

## 4. 筛选流程、排期与资源

从资料完整且授权确认之日起，建议在 7～10 个工作日内完成；等候补证暂停计时并记录原因。

| 阶段 | 时间安排 | 工作内容 | 产物与进入下一阶段条件 |
| --- | --- | --- | --- |
| S0 岗位校准 | 批次启动前半天 | 冻结职责、题目、门槛；用同一示例校准评分 | 岗位说明、评分版本、面试官分工 |
| S1 资料与年限初核 | 第 1～2 日；20～30 分钟沟通 | 去重时间线、缺口、候选人授权；确定能否达到门槛 | 初核表；明确不足则停止本岗流程，不占用长面试 |
| S2 项目与架构深挖 | 第 3～4 日；75 分钟 | 生命周期、本人主导的架构、两个技术难题 | 案例证据表、初评分；关键责任说不清则补证 |
| S3 现场编码与调试 | 第 4～6 日；90 分钟 | 标准实验仓库实现、测试、故障定位和变体 | 代码差异、执行输出、观察记录 |
| S4 调优与协作 | 第 6～7 日；60 分钟 | 真实性能案例、分批给证据的诊断、评审/协作模拟 | 调优报告、协作行为评分 |
| S5 授权核验与复核 | 第 7～9 日 | 交叉核实时间/职责，独立评分再讨论 | 年限结论、证据置信说明、分歧处置 |
| S6 名单与反馈 | 第 10 日内 | 人工决定合格建议、待补证、未达标，提供事实更正机会 | 合格名单、个体报告、缺口清单 |

候选人同步投入约 4～4.25 小时，分场次安排，不要求无偿完成真实业务需求。较长作业应提供等价现场题或合理补偿安排。

资源：招聘协调人 1 名、技术面试官 2 名（至少一名覆盖岗位主栈）、招聘负责人 1 名；可兼任但不能省独立评分。每名候选人预计消耗约 8～10 内部人时，按面试官同时出席和核验情况校准；默认分拆两位面试官负责不同场次，不必全程双人陪同。

试题环境：预装依赖、合成数据、可重置测试库、无生产凭证；题库至少两套同难度变体。录音/录像仅在明确告知并获同意后进行，不以不同意录制自动淘汰。

## 5. 项目与架构核查题

### 5.1 如何判断中大型项目

不以公司名气、团队人数或某个 QPS 数值单独认定。至少记录两个能实证的复杂度维度：跨团队/外部集成、数据量与一致性、业务关键性与恢复、长期迁移兼容、监管/权限、部署与运行约束。该要求是本评估口径，不是行业统一规模定义。

让候选人逐一说明：用户/业务边界、时间跨度、团队与职责、关键接口/数据、容量指标口径、失败代价、生命周期各阶段的本人工作。

### 5.2 生命周期与个人贡献

| 环节 | 核心追问 | 合格证据 | 需继续核实的信号 |
| --- | --- | --- | --- |
| 需求 | 哪个模糊要求由你转为可验收条件？ | 业务约束、异常与验收例子 | 只说“按产品文档做” |
| 设计 | 为什么选该边界？否决过什么？ | 备选方案、代价、数据所有权 | 只有技术名词和架构图 |
| 开发 | 你亲自实现/评审哪个关键模块？ | 函数/数据结构/事务边界与边界测试 | 无法区分本人和团队工作 |
| 测试 | 什么错误曾逃过测试，后来怎么补？ | 正反例、覆盖盲点、回归结果 | 只说“测试同学负责” |
| 发布 | 如何迁移数据、分批发布和回退？ | 兼容顺序、发布门禁、止损 | 回滚只理解为重新部署旧包 |
| 运维 | 你参与过什么故障、怎样恢复？ | 时间线、证据、影响、沟通 | 只有“加机器/重启”而无解释 |
| 演进 | 方案何时不再适用，怎样替换？ | 后续变化、成本/风险、迁移结果 | 宣称没有缺点或没有失败 |

### 5.3 主导架构案例，至少一个

让候选人先用 10 分钟重建方案，再逐步改变约束：负载翻倍、下游超时、业务数据不能丢、旧客户端不能同时升级、预算减少。要求解释：

1. 原需求与质量属性，哪些是数据、哪些是估算。
2. 自己拥有的决策权、实际提交/评审/协调工作，谁负责其余部分。
3. 单体或服务边界、契约、事务、异步、权限和观测如何落实。
4. 为什么不选另一个方案，什么条件会改选。
5. 从设计到上线的分阶段计划、兼容、迁移与失败恢复。
6. 结果如何测量，以及目前仍未解决的限制。

不把“担任架构师”当作证据；也不要求必须做微服务。能证明模块化单体更适合业务，同样可以通过。

### 5.4 复杂问题的深度与广度

每人提供两个不同层面的真实案例，例如应用并发与数据库锁、前端渲染与网络、MQ 消费与跨服务一致性。深挖一个到机制/代码级，再用变体检验另一个；不要求精通全部框架。

统一顺序：现象 -> 影响 -> 时间线 -> 首个假设 -> 收集的证据 -> 被排除的原因 -> 根因 -> 修复 -> 同条件复测 -> 长期预防。不能以能背术语代替完整证据链。

## 6. 实际编码与调试

### 6.1 统一规则

使用准备好的、与真实公司业务无关的小型仓库。提前说明语言/版本、允许文档、AI 使用规则和评分标准。主考核 60 分钟独立修改与测试，后续 30 分钟调试/变体与解释；先澄清题意，不以打字速度作为核心指标。

主考核默认可查官方文档、不用生成式 AI；如岗位要求评估 AI 协作，可另加短环节并单独记录。允许 AI 时也要现场解释、修改变体与复测；不得用 AI 产物直接证明个人独立编码能力。所有人同一规则。

### 6.2 岗位题 A：Java/服务端

预置 Spring/数据库/测试工程，完成库存预留接口：

- 同业务键重复请求不重复扣库存，同键不同参数返回约定冲突。
- 不同请求并发竞争库存时不超卖，错误结构可解释。
- 在真实测试数据库里检验成功、并发、非法输入、重复和异常回滚；基础环境由面试方提供。
- 追加变体：提交成功后响应丢失，或消费者重复执行，要求画出恢复策略。

90 分钟内评估的是一个受限增量，不要求从零搭完整分布式系统。重点看约束、事务边界、参数绑定、测试断言、错误处理和能否解释自己写的代码。

### 6.3 岗位题 B：React/Vue/平台前端

预置 TypeScript 页面和可控制延迟的 API，完成列表筛选与编辑：

- 快速切换筛选时旧请求不能覆盖新结果。
- 编辑失败保留输入；刷新时按约定恢复状态，权限在服务端契约中明确。
- 修复一处错误 key/状态复用或响应式/Effect 清理问题。
- 加组件测试，验证加载、错误、竞态和键盘操作；解释测试观察的行为。

主框架按岗位选择。若岗位明确要求 React/Vue 双精通，应另对另一框架做等价小变体并提前增加面试时间，不允许用一道 React 题自动判 Vue 达标。

### 6.4 编码行为评分证据

记录候选人的需求澄清、分步定位、代码结构、关键测试、复杂度/资源解释、工具使用及主动发现的局限。面试官统一分级提示并记录提示次数；环境故障暂停计时，不归咎于候选人。

关键扣分应指向观察事实，例如“同键异参测试失败”，不能写“感觉资历不足”。缺少某 API 记忆但能正确查文档不等于能力不足；无法解释自己的实现或在变体下保持正确性才是重要信号。

## 7. 系统调优与协作验证

### 7.1 调优

真实案例必须说明环境、数据量、请求比例、指标定义、基线、变化、复测与副作用。能披露区间而非精确数字；没有可核验数据则写证据局限，不能强迫泄露业务信息。

桌面诊断题：“发布后 p99 上升，CPU 不高，连接池等待增加。”依次提供指标、线程状态、慢 SQL 和变更信息，评估候选人会要求什么证据，如何区分阻塞、池配置、长事务和下游慢。

通过要求：先说明影响与必要止损；提出能证伪的假设；不盲目加线程/连接；复测同时看正确性、成功吞吐、尾延迟、错误/拒绝、资源和成本。生产应急不要求为了单变量实验延误恢复。

### 7.2 团队协作

至少问两个真实行为案例，并做一次 10 分钟评审模拟：

- 设计被同事反对时，你怎样处理分歧？谁改变了什么？
- 需求临时变化而发布日期不变，你如何拆范围并说明风险？
- 一次你的判断造成返工/事故，如何沟通和防止复发？
- 如何让另一位工程师接手模块？给出实际文档、评审或辅导方法。

评审模拟给一段有缺陷的改动，观察能否指出风险、解释理由、提出可执行修复，并听取新证据。评价行为和结果，不以外向、口音、表达风格或是否认同面试官作为标准。

## 8. 评分、校准与决定

各维度先按 0～5 级评分，再计算 `加权分 = 等级 / 5 × 权重`。允许半级，但必须记录对应事实。

| 等级 | 行为锚点 |
| --- | --- |
| 0 | 已完成考核但无法解释或实现核心要求；未考核则记未评估，不记 0 |

## 9. 信息安全与 AI 使用边界

本仓库面向公开发布，只保存匿名流程、题目和空白模板。真实简历、证明人联系方式、面试记录、名单和个体报告应存放在组织批准、权限受控的招聘系统中，不写入本仓库或公开变更记录。

仅收集岗位所需材料，确定可访问角色、保存期限与删除流程。可采用“招聘结束后 90 天复核删除”的初始方案，但必须结合当地法律、公司政策与候选人同意调整；人才库长期保留需要单独依据。

AI 可以按提供的材料整理时间线、标出冲突、草拟追问和报告；不得凭照片/声音/姓名推断年龄、人格或背景，不搜索私人资料，不独立做录用决定。未经允许不能把公司保密案例上传外部模型。
